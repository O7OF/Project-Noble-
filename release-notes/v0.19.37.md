# Project Noble v0.19.37 Release Notes

## Single-Window (Container) Launcher: Focus, Input and Frame Rate
- **The match finally gets the focus, not just the window.** In container mode the match renders into a `WS_CHILD` window
  inside the launcher's top-level window, so `GetForegroundWindow()` can never equal it. Every focus test now goes through
  `Window::IsForeground()` (the window is the foreground one, or the foreground window is an ancestor of it), and the match
  window joins the launcher's input queue (`AttachThreadInput`) and takes `SetFocus` — re-asserted at most once a second while
  the launcher is in front.
  - Cutscene skip, pause menu, mouse look and movement work again; the 30 FPS background throttle no longer applies to a match
    running inside the launcher.
  - Also fixed for push-to-talk, social chat, pad navigation and "mute in background", which all used process-id checks.
- **Leaving a match returns to Noble's menu.** The launcher marked its overlay closed when the match started and never cleared
  it, so it came back showing MCC's raw `mainmenu_all` map. The flag is cleared on restore, and the launcher takes the keyboard
  focus back from the match window.
- **PLAY AGAIN / NEXT MISSION inside the container.** A hosted match can no longer spawn an unsupervised successor while the
  launcher brings its own menu back over it (and `HandOff` no longer waits 30 s for a top-level window a child never has).
  The match records the successor's arguments in `data\userdata\container-relaunch.txt` and the launcher starts it.
- **Exclusive full screen** is not attempted for a hosted child window, and a hosted child never restyles itself.

## Crash Fixes
- **Multiplayer/custom launch crash `0xE06D7363`.** `UiArt::LoadingBackground` took `s_mutex` and then called `PackImage`, which
  locked the same non-recursive mutex; MSVC reported "resource deadlock would occur" as an uncaught exception 340 ms into a
  match launch. The Armory's art cache now uses a recursive mutex (`UiArt.cpp`). Campaign only survived because it returns
  early from a matched loading-scene CRC.
- **Armory crash in the NVIDIA shader compiler (`0xC0000005` in `nvgpucomp64.dll`).** A rank-locked visor was reset to DEFAULT
  every frame while `SyncLegacyFields()` restored it from `m_visorSelection`; the resulting ~60 profile saves per second
  re-applied the player profile continuously. The fallback is now recorded in `m_visorSelection` as well and a row already on
  its fallback is skipped, so a locked item falls back once. This was also why "previewing a helmet un-equips it again".
- **Spam-buying Armory items crashed the game.** Every change requested a biped rebuild from the menu map's script while the
  previous one was still in flight. Rebuilds are now serialised (one at a time, pending changes coalesced, gated on the
  script's own `REMADE` counter and a quiet window): 22 helmet changes at 40 ms now produce 4 rebuilds instead of 22.
- **Unhandled C++ exceptions now leave evidence.** The CRT answers them with a fail-fast (`0xC0000409`) that the SEH crash
  handler never sees; a `std::terminate` handler logs the exception's `what()` and a 24-frame stack with module RVAs.

## Armory
- **One camera rule, no modes.** Species and Body (and Elite) show the whole body; every other row uses the map's preset camera
  for that part (`c_helmet`, `c_chest`, `c_left/right_shoulder`, `c_wrist`, `c_utility`, `c_knees`). The C key, mouse wheel
  and "Camera: CLOSE-UP / FULL BODY / ARMORY VIEW" badge are gone.
- **The character can be turned in every camera.** The pedestal turn and the model's yaw are re-written every frame (the map
  script used to snap them back in the close-ups), so drag and Q/E rotate the model under a fixed close-up camera too.
- **Framing.** Whole-body zoom 1.5× → 1.12× with the model centred lower, so the helmet clears the player card and the boots
  stay on screen.
- **Credit balance** is shown as `CR: 19,445,000` next to the nameplate on the Armory screen.
- **Tried-on pieces stay applied** while a preview is active, and the resolved Armory selection is saved to
  `data\userdata\armory-selection.json` so a match process (which never runs the Armory) applies the right visor and colours.
- **GRD helmet.** The AKIS helmet is a normal Armory item again: **Eclipse** rank and **777,777 cR**; each AKIS attachment
  (GRD, GRD/CBRN, CBRN) is **7,777 cR**. The developer-only lock and the dev-menu unlock button were removed.
- **Campaign NPC Spartans keep their canonical colours.** The in-game material sync is skipped for campaign missions; it used to
  paint the player's undersuit, armour lights and visor onto every AI Spartan in the level.

## Multiplayer Appearance
- **Other players no longer look like you.** The colour sync only forces colours onto the **local** player's biped
  (`player_mapping_get_unit_by_output_user(0)`), and only when the look uses wheel (custom RGB) colours. Palette colours and the
  30-visor index travel in each player's appearance record and are rendered per player.
  - Wheel colours remain local-view only (the engine's materials are shared), which is the only way to show them at all.

## Pre-Game Lobby (Custom Games & Forge)
- **Team dividers, always.** When the game type assigns teams, the roster is a single Reach-style list with a coloured divider
  bar per team — shown even when you are alone in the lobby, with an OPEN row under an empty team.
- **Multi-team support.** Halo: Reach's eight teams share one palette (`TeamColors.hpp`): Red, Blue, Green, Orange, Purple,
  Gold, Brown and Pink, used by the lobby dividers and the player rows.
- **TEAM COUNT** (host, 2..8) and **CHANGE TEAM** rows in the lobby options, plus a "SWITCH TO <TEAM>" button on the player
  card, so players can be moved between any of the mode's teams. The host's manual choices are not re-dealt.
- **Forge lobbies now read their teams** (`RefreshLobbyMode` ran only for Custom Game), so Forge shows the same dividers and
  team controls.
