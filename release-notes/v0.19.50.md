# v0.19.50

## Joining a lobby no longer inherits the last lobby's mod

Two bugs made a guest launch the wrong map, which is what failed both tests: joining a Forge-mod lobby and co-op
campaign with no mod.

- **Stale mod on the host's session.** The master server keeps a session's Workshop item when a re-registration
  does not mention one, and the client only sent `mod_id` when it had a mod. A host that went from a modded map back
  to a stock one kept advertising the old item, so guests were told to look for that mod's maps. Both sides now send
  the field explicitly, and the server treats an explicit empty value as "no mod".
- **Stale map override on the guest.** A map override (the mod's `.map` served in place of a stock map) survived from
  one lobby into the next. In the test, the guest joined a campaign co-op lobby and launched `m35` with the previous
  lobby's `cex_ff_halo_normal.map` overlaid: the engine loaded, then bailed at the end of the intro - the reported
  co-op error. Overrides are now cleared when entering a lobby, and an override is ignored if it does not belong to
  the map being launched.
- **A missing mod map is refused instead of launched.** When the guest cannot find the host's mod map, the client no
  longer starts the match on the plain map (which desyncs or errors); it stays in the lobby and logs which Workshop
  item is missing.

Campaign, Forge and multiplayer launches on a single machine are unaffected (verified).
