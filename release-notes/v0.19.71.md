# Project Noble v0.19.71 Release Notes

## Fix: Fatal stack overflow a few seconds into the menu / a match

### Symptom
The game died with `0xC00000FD` (STATUS_STACK_OVERFLOW) inside `haloreach.dll`, typically a few seconds
after the main menu appeared or shortly after a match started:

```
FATAL EXCEPTION CAUGHT: Code 0xC00000FD at Address 0x7FFCA7510B74 (+0x150B74) (Module: haloreach.dll)
 Frame 07: 0x7FFCA7510B74 (+0x150B74) [haloreach.dll]
 Frame 08..31: 0x7FFCA7510B91 (+0x150B91) [haloreach.dll]   (repeated)
```

The crash was not reproducible with stock engine limits, but hit every run with
`extendedLimits` 1-3 (in particular `Full` + `aiActors 1024`).

### Root cause
`haloreach+0x150A30` is the recursive half of the engine's *objects near this object* query
(`0x1D6380 -> 0x150BC0 -> 0x150A30`). It walks one collision-hierarchy node, collects the node's
collision elements, then recurses into both children (`node+0x10`, `node+0x14`, a child of `-1` ends
the walk). Every level costs `0x70` bytes of stack.

The 0x1C-byte nodes (`collision hierarchy node header` pool) and 0x30-byte elements (`collision
hierarchy element headers` pool) are shared, recycled records. When the hierarchy being walked holds a
stale child handle - a node that was freed or re-initialised while its parent still points at it - the
target record is all zeroes, and a zeroed record's child fields read as node `0` instead of `-1`. The
walk then loops: `0 -> 6 -> 5 -> 4 -> 0 -> ...` until the thread's 1 MB stack is gone (9,130 nested
frames were measured in the captured dump). The extended object pool (2,048 -> 32,767 slots) changes
which object slots the Armory's model rebuild recycles, which is why the loop appeared only with
extended limits enabled.

### Fix
New crash guard, `src/host/CollisionWalkGuard.cpp`: `haloreach+0x150A30` is detoured once at load time.
The detour keeps a per-thread recursion depth and refuses to descend past 512 levels (or within 64 KB of
the thread's stack limit), returning "no objects found" for that subtree. A healthy hierarchy is tens of
nodes deep, so nothing observable changes; a damaged or cyclic hierarchy now costs a few nearby-object
lookups instead of the whole process. The first eight bails are logged:

```
Collision walk guard: collision hierarchy is cyclic or stale (node XXX, 512 levels deep); stopping this walk instead of overflowing the stack
```

### Verified
* Repro: dev build under a debugger, `extendedLimits 3` / `aiActors 1024` -> `0xC00000FD` within 8-35 s
  of the menu, 3 runs out of 3 (9,130 nested `0x150B91` frames captured in a full-memory minidump).
* A/B: the same build with the guard removed crashed again on the same chain
  (`0x1D6415 -> 0x150D67 -> 0x150B91 ...`); with the guard, 3 runs of 120-150 s stayed up and the guard
  logged the bails (`EF670004` - the handle that points at the zeroed node in the dump).
* Stock limits (`extendedLimits 0`) were already unaffected and stay unaffected.
